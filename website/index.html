Scroll to advance time

Trials expire. Sessions time out. Renewals, dunning, retention purges and webhook retries all wait for a date. Time-dependent code is some of the least-tested code in any SaaS product.

How it gets tested today:

  • Editing timestamps in the database by hand
  • Shortening durations with a test-only flag
  • Waiting real days in staging
  • Not at all

None of these exercise the real interaction between the database's now(), Redis expiry, your schedulers and your services.

One clock for the whole stack.

Every service reads the same virtual time. Advance it, and the jobs that depend on it actually run, at the virtual time they're due.


            

            
          

        

      

    


    
    

      
How it works


      

        

          
        

        

          
One clock for every service.

          
A small C library loaded with LD_PRELOAD makes wall-clock reads (now(), Date.now(), time.time(), Redis expiry) return virtual time. It adds about 13 ns per read. Monotonic clocks are left alone, and absolute deadlines are translated back to real time, so locks and timeouts never hang.

        

      


      

        

          
        

        

          
Moving the clock runs your scheduled work.

          
Changing the clock doesn't fire timers. So advance stops at each interesting virtual time, runs the triggers you declare (“the nightly job at 03:00”), and waits on barriers (“the queue is empty”) before moving on. pg_cron is detected and handled automatically.

        

      


      

        

          
        

        

          
Everything is verified.

          
After each advance, every service is probed to confirm it sees the new time, and chronostack doctor explains anything it can't reach.

Script the outage.
Assert the outcome.

        
Scenarios are repeatable tests in virtual time. Take the partner's webhook receiver down on day 14 from 02:00 to 06:00, advance, and check that the webhook was retried and delivered exactly once.

      

      

        
steps:
  - fault: { target: webhooks, from: +14d2h, for: 4h }   # partner down on day 14, 02:00–06:00
  - advance: 14d
  - advance: { by: 12h, step: 1h }
  - assert:
      redis:
        service: cache
        command: [HGET, webhook:received, "trial.expired:${user_id}"]
        equals: "1"

Built to sit on the stack you already have.

      

        
No code changes
Works on your existing compose.yml, as a separate copy. Your containers, data and files are untouched.

        
Scheduler-aware stepping
Triggers run at their exact virtual times. BullMQ and Celery beat fire on their own, and pg_cron jobs are never skipped.

        
Outages in virtual time
A small proxy in front of HTTP dependencies makes “the payment API is down on day 3 from 09:00 to 11:00” a one-liner.

        
Scenarios and reports
YAML steps with SQL, Redis, HTTP and exec checks. JSON and Markdown reports.

        
CI ready
Exit codes, a GitHub Action, and a strict mode.

        
AI agents
chronostack mcp is an MCP server with a fixed, safe tool set.

        
Host-native Node
node -r sdk/node/register.js app.js puts a Node process outside Docker on the same clock.

        
Safe by design
Never changes the host clock, needs no privileged containers, gives no container the Docker socket, and its API is local-only with a token.

Questions.

      

        

          
Does ChronoStack change my computer's clock?

          
No. It never touches the host clock and needs no privileged containers. Virtual time exists only inside the copy of your stack that ChronoStack starts: a small library loaded with LD_PRELOAD makes wall-clock reads in those containers return virtual time.

        

        

          
Do I have to change my code or my compose file?

          
No. ChronoStack works on your existing compose.yml, as a separate copy, and leaves your containers, data and files untouched. When a scheduler needs help firing at the right virtual time, that's one line of YAML (a trigger).

        

        

          
Which languages and databases does it support?

          
Tested in CI: PostgreSQL 16 (including pg_cron), Redis 7, Node.js 22 and Python 3.10 / 3.12. JVM 21 passes a no-hang suite and is otherwise experimental. Node.js 20, Python 3.13+, JVM 17, Ruby 3.x and MariaDB are expected to work but aren't covered by tests.

        

        

          
Does it work with Go?

          
Not yet. Go and other static or setuid binaries don't load LD_PRELOAD libraries, so their clocks can't be redirected. chronostack doctor flags them.

        

        

          
Why doesn't my app's timer fire when I advance the clock?

          
Changing the clock doesn't fire timers that are already waiting. So advance stops at each interesting virtual time and runs the triggers you declare, such as “the nightly job at 03:00”. BullMQ, Celery beat and pg_cron fire on their own; node-cron, APScheduler and setTimeout-style loops need a trigger.

        

        

          
Can I move time backwards?

          
No. Virtual time only moves forward, the way real deadlines, expiries and logs expect it to.

        

        

          
Can I run it in CI?

          
Yes. Scenarios return exit codes and write JSON and Markdown reports, there's a GitHub Action, and a strict mode for pipelines.

        

        

          
Does it work on macOS or Kubernetes?

          
macOS (Docker Desktop, OrbStack) should work but is untested; issue #5 has a 5-minute test if you can help. Kubernetes is out of scope for the 0.x releases; ChronoStack targets Docker Compose.

        

        

          
Is it free?

          
Yes. ChronoStack is open source, licensed under MIT or Apache-2.0, at your option.

        

      

    


    
    

      

      

        
Install in one line.

        
You need Docker with Compose v2. No admin rights needed. The installer verifies checksums and puts chronostack on your PATH.


        

          

            
            
          

          

            
curl -fsSL https://github.com/Asmodeus14/ChronoStack/releases/download/v0.1.0-alpha.2/install.sh | CHRONOSTACK_VERSION=0.1.0-alpha.2 sh

            
          

          

            
$env:CHRONOSTACK_VERSION = "0.1.0-alpha.2"; irm https://github.com/Asmodeus14/ChronoStack/releases/download/v0.1.0-alpha.2/install.ps1 | iex

            
          

        


        

          
Then run the demo

          
A small SaaS app with a 14-day trial, a nightly job and webhooks.

          

            
git clone https://github.com/Asmodeus14/ChronoStack && cd ChronoStack/examples/saas-trial-demo
chronostack up --wait
chronostack advance 15d        # the trial expires at the nightly job
chronostack run scenarios/trial.yml
